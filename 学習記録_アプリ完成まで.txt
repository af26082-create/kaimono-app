2. 自分から質問したポイント
======================================================================

Q. map の中身の書き方が分からない
   → 段階的に組み立てる。
     ① 普通のJSとして numbers.map((n) => n * 2)
     ② オブジェクトの配列で users.map((u) => u.name)
     ③ 返すものをJSXにする
     ④ JSXの中に {} で置く
     ⑤ 長くなったら (  ) で囲んで改行
   最後の ))} は、内側から順に閉じているだけ。

Q. props がよく分かっていない
   → props は「関数の引数」そのもの。
     <ItemCard item={x} /> は ItemCard({ item: x }) と同じ。
     詳細は メモ/props.txt にまとめた。

Q. setItems の使い方が分からない
   → 「置き換える」命令。元の配列を書き換えず、新しい配列を渡す。
     更新は .map()、削除は .filter()、追加は [新しいもの, ...元の配列]。

Q. useEffect の第2引数とは
   → 引数はカンマで区切られた順に数える。
     useEffect(関数, 依存配列) の2つ目。
     }, [items]) の並びは「関数を閉じる } / 区切りの , / 第2引数 / 呼び出しを閉じる )」。

Q. filter の中の条件式が分からない
   → コールバックは「残すか？」を true/false で返す。
     削除は「消す」ではなく「それ以外を残す」と考える。

Q. 型チェックのやり方
   → VS Code の問題パネル（Ctrl+Shift+M）、npx tsc -b、npm run build。
     tsc は成功すると何も表示しない。

(2) import を1つも書いていなかった（Item 型、ItemCard）

(3) return の直後に {} を書いた
    → {} がスイッチとして働くのは JSXタグの内側だけ。

(4) ItemCard に props をバラバラに渡そうとした（{item.name} など）
    → JSXの属性は「名前=値」の形。そして ItemCard は item を丸ごと受け取る設計。

(5) ItemCard を開始タグ+終了タグで囲み、中身を渡した
    → ItemCard は children を受け取らない。自己閉じタグ <ItemCard ... /> にする。

(6) key={item} とオブジェクトを渡した
    → key には項目ごとに固有の文字列（item.id）を渡す。

(7) 関数の中身をカンマで区切った（}, の形）
    → カンマで区切るのはオブジェクトや配列。関数の中は文を並べる場所。

(8) App.tsx に ItemList の中身を書いてしまった
    → item / onToggle / onDelete は ItemList の中だけで使える名前（スコープ）。
      App が書くのは ItemList の props。

(9) import ItemCard from './components/ItemList' と、中身と違う名前で読み込んだ
    → default export は名前を自由に付けられるのでエラーにならず、混乱の原因になった。

     → これらは値を変換しない。文字列を渡すと常に想定外の結果になる。

     → 何でも打ててしまい、as Category の保証が崩れる。<select> にする。

(37) Category 型の import を忘れた
     → import はファイルごとに必要。他のファイルで読み込んでいても使えない。

4. 新しく覚えたこと
======================================================================

【配列の3つの命令】
  .map()     配列 → 配列（全要素を変換する）
  .filter()  配列 → 短い配列（条件が true のものだけ残す）
  .reduce()  配列 → 1つの値（合計などにまとめる）
             第2引数の初期値を省略すると、空配列でエラーになる

【key】
  .map() で並べた要素に必要。React が要素を見分けるための目印。
  index を使うと、削除したときに状態がずれる。データの id を使う。

【useState】
  const [値, 値を変える関数] = useState(初期値)
  setX を呼ぶと再描画される。setX を通さない変更は画面に反映されない。
  だから配列やオブジェクトは書き換えず、新しいものを作って渡す。
  初期値に重い処理を書くときは useState(() => 処理()) の形にする。

【useEffect】
  useEffect(実行したい処理, 依存配列)
  依存配列に書いたものが変わったときに実行される。
  [] なら初回だけ。省略すると毎回実行され、無限ループの原因になる。

【フックのルール】
  ・コンポーネント関数の中でしか呼べない
  ・if やループの中で呼んではいけない
  → 呼ばれる順番で管理されているため。破ると実行時エラーで画面が真っ白になる。

【制御されたコンポーネント】
  value と onChange（checked と onChange）は必ずセット。
  「見た目は state が決める、操作は state を変える」という一方通行にすると、
  画面とデータがずれない。

【スプレッド構文】
  { ...item, status: 'bought' }   オブジェクトをコピーして一部を差し替える
  [newItem, ...items]             配列の先頭に足した新しい配列を作る
  元のものは変更しない。これが React で重要。

【早期リターン】
  条件に合わなければ return して、その先を実行しない。
  ItemList の0件表示、ItemForm の入力チェック、編集の空欄チェックで使った。
  条件の入れ子が深くならず、以降を「問題なし」の前提で書ける。

【派生データ】
  plannedItems / boughtItems は state にせず、items から計算で作る。
  合計金額を保存せず計算するのも同じ考え方。
  元になるものを1つだけ持ち、そこから導けるものは計算する。
  → 同期のズレが原理的に起きない。

【下書き（draft）とデータの分離】
  編集中の値は ItemCard の中に draft として持ち、
  保存ボタンを押したときに初めて親へ渡す。
  キャンセルは「渡さない」だけで済む。

【状態の置き場所】
  データ（items）        → App が持つ（唯一の事実）
  UIの状態（isEditing）  → その部品が持つ（他に影響しないため）

【localStorage】
  文字列しか保存できない。
  保存：JSON.stringify   読み込み：JSON.parse
  JSON.parse は壊れた文字列で例外を投げるので try / catch で囲む。
  getItem の返り値が null（未保存）と '[]'（空という状態）は別物。

【フォーム】
  <form> を使うと Enter キーで送信できる。
  ただし既定でページを再読み込みするので e.preventDefault() で止める。
  form の中の <button> は既定で送信ボタンになる。

【文字列と数値の境界】
  入力欄は常に文字列（e.target.value は必ず string）。
  Item は数値で持ちたい。だから境界で変換する。
    入力 → 保存   Number(...)
    データ → 編集欄  String(...)
  単価や個数を数値の state で持つと、欄を空にできなくなる。

【入力チェックで使うもの】
  .trim()             前後の空白を取り除く。空白だけの入力を弾ける
  Number('')          0 になる。空欄チェックを別に行う必要がある
  Number.isNaN(値)    値が NaN そのものか。変換しない
  Number.isInteger(値) 整数か。変換しない
  !条件               否定。=== false より短く書ける

【TypeScript】
  型アサーション  e.target.value as Category
    「この値をこの型として扱え」とチェックを黙らせる書き方。
    HTMLの構造から確実に安全な場面だけで使う。乱用すると型の意味がなくなる。
  import はファイルごとに必要。export していても、読み込まないと使えない。
  型は import type、値は通常の import。

【スコープ】
  変数は宣言された場所の中でしか使えない。
  同じ名前を付けると外側が隠れる（シャドーイング）。

【自動セミコロン挿入】
  return の直後に改行があると、そこで文が終わったと解釈される。
  だから return ( と丸括弧を同じ行に書く。

【CSS】
  display: flex        親としての指定（子を横に並べる）
  flex-direction       column にすると縦並び
  flex-wrap: wrap      入りきらなければ折り返す
  flex: 1              子としての指定（親の余った幅をもらう）
  gap                  子要素の間隔
  CSS変数              :root に --color-xxx を定義し var() で使う
                       色を1か所で決める（値を2か所に書かない原則）
  <label> で囲むと、ラベルをクリックしても入力欄にカーソルが入る

5. デバッグで身についたこと
======================================================================

・画面が真っ白になったら、まず F12 → Console を見る。
  実行が止まった理由が書かれている。画面には何も出ない。

・エラーは一番上から直す。構文エラーは連鎖するので、
  1つ直すと10個消えることがある。

・型チェックが通っても正しいとは限らない。
  （<h1> の中に <h1> を入れてしまった例。タグの意味までは見ていない）

・エラーメッセージは正解を教えてくれることがある。
  「Did you mean 'items'?」のような提案は信用してよい。

・Shift + Alt + F で整形すると、入れ子の間違いがインデントで見える。

・1つ足すごとにブラウザを見る。まとめて書くと、どこで壊れたか分からなくなる。

・「直したのに変わらない」ときは、保存されているかを疑う。
  （VS Code の自動保存を有効にして解決した）
